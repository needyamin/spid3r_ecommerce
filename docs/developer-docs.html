1. What Is This Project?

A full e-commerce store (storefront + admin panel) built on the Spid3r language and the Spid3rWeb MVC framework.

Spid3r Store is a production-style online shop written in Spid3r (a Rust-hosted language, files end in .matrix) and running on Spid3rWeb 1.1.1 — an MVC framework with an Active-Record ORM, the SpiderBD template engine (.bd.html), session/JWT auth, caching, queues and a CLI (magic). Customers browse a storefront, fill a cart, check out and pay through sandbox payment gateways; staff manage everything from a pure-AJAX admin panel.

StorefrontHome with featured products, catalog with filters, product pages with gallery & variants, category/brand pages, cart, checkout, order tracking, returns, support.
Admin PanelDashboard KPIs, products (gallery/variants/SEO), inventory, orders, customers, staff & roles, coupons, shipping zones, payment lab, audit log, reports.
PaymentsSSLCommerz, Stripe, bKash and Nagad (sandbox) plus a built-in simulator for development.
Platform44 relational tables, queued e-mail/SMS jobs, RBAC permissions, CSRF protection, rate limiting, audit logging.

3. How The Website Works (User Journey)

What actually happens when a customer and an admin use the site.

Customer side

  1. Browse — StorefrontController renders the home page (featured products from the catalog, cached by CatalogCache), catalog listings with filters, product detail pages (gallery, variants, stock availability), category and brand pages.
  2. Cart — guests get a signed cart-identity cookie (CartIdentity); CartController + CartRepository persist cart rows. When the guest registers/signs in, the guest cart merges into the account cart.
  3. Checkout — CheckoutController + CheckoutService collect the address, compute the shipping-zone fee (ShippingService), apply coupons (CouponService) and gift cards (GiftCardService), then place the order (OrderService) which reserves stock (InventoryService) and queues the confirmation e-mail.
  4. Pay — PaymentService hands off to a gateway (sandbox); the callback URL confirms the payment and the customer lands on the confirmation page and can track the order at /track.
  5. After-sales — order history, invoices (/orders/<id>/invoice), returns (ReturnService), support tickets (queued acknowledgement e-mail).

Admin side

  1. Sign in as a user with the admin role — every admin route is gated by middleware("role:admin") and fine-grained permission:catalog.manage, customers.manage, settings.manage, reports.view gates.
  2. The dashboard aggregates revenue, order pipeline and low-stock alerts directly from the database — no mock data anywhere.
  3. public/js/admin.js is a pure-AJAX SPA: every create/edit/delete/toggle goes through /admin/api/* JSON endpoints with a _csrf token — zero full-page reloads.

From HTTP packet to rendered response. Source: docs/diagrams/request-lifecycle.mmd

7. SpiderBD Template Engine

The view engine behind every page: framework/View/BD.matrix + TemplateCompiler.matrix / TemplateEvaluator.matrix. Templates live in resources/views/**/*.bd.html, are compiled once and cached, then evaluated against the controller's context map.

Output & escaping

SyntaxBehavior
{{ product.name }}Prints a value, HTML-escaped (safe against XSS by default)
{!! trusted_html !!}Prints raw HTML — only for content you control (e.g. generated SVG)

Control flow

@if(in_stock)
  <span class="stock-badge">In stock</span>
@else
  <span class="stock-badge">Out of stock</span>
@endif

@if(qty > 0)
  …
@elif(low_stock)          <!-- also spelled @elseif(...) -->
  …
@endif

@foreach(inv in inventory_rows)
  <tr><td>{{ inv.product_name }}</td></tr>
@endforeach

Layout inheritance

<!-- child template: resources/views/store/home.bd.html -->
@extends("layouts.store")

@section('title', store_name)      <!-- inline section (value form) -->
@section("content")                <!-- block section -->
  …page markup…
@endsection                        <!-- "@stop" also works -->
<!-- layout: resources/views/layouts/store.bd.html -->
<title>@yield("title") · {{ store_name }}</title>
@yield("content")                  <!-- with an optional default: @yield("meta_description", "fallback") -->

Partials & form helpers

@include("partials.product_card")  <!-- dot notation → resources/views/partials/product_card.bd.html -->

@csrf                              <!-- → <input type="hidden" name="_csrf" value="{{ csrf_token }}">
@method("PUT")                     <!-- → <input type="hidden" name="_method" value="PUT"> (HTML-form override)

How a view gets rendered

  1. Controller builds a context map (plain values + nested maps/lists, pre-shaped for the template: display strings, booleans like is_published, URLs).
  2. view("admin/table", ctx) (from framework/Web) resolves resources/views/admin/table.bd.html.
  3. The compiler handles layout inheritance (@extends/@section/@yield), splices @include partials and expands form directives.
  4. The evaluator resolves @if/@foreach against the context and replaces {{ … }} / {!! … !!} expressions (dot-notation access into maps).
  5. Compiled templates are cached; the result is returned as an HTML Response.
Convention in this project: controllers pass pre-computed display values (price_display, available, is_low_stock, product_url) so templates stay logic-light — conditionals only choose which pre-shaped values to show, they never compute business rules.

14. Queue, Mail & SMS

Nothing blocking in the request path — notifications are queued.

Job namePurpose

Handlers are registered in routes/queue.matrix (imported by both entry points). The default sync driver executes jobs in-process; mail uses the log driver in development so messages are recorded in storage/logs/mail-*.log instead of being sent.

16. Testing

44 suites covering framework internals, store units, integrations, E2E and adversarial cases.

# Recommended: testing env keeps the cache in-memory (no rate-limit pollution between suites)
APP_ENV=testing SPID3R_PATH=. spid3r run tests/test_store.matrix      # single suite
APP_ENV=testing SPID3R_PATH=. spid3r run tests/run_all.matrix          # framework suites via TestRunner
APP_ENV=testing SPID3R_PATH=. spid3r magic test                        # all registered suites
  • Store suites (test_store_*.matrix, test_admin_*.matrix): boot the real app with TestClient, seed their own data, exercise HTTP flows and assert on responses and database state.
  • E2E (test_admin_e2e.matrix): all 8 admin modules through the real HTTP stack.
  • Adversarial (test_admin_adversarial.matrix): 422 validations, uniqueness, CSRF, RBAC and abuse cases.
  • Skips by design: test_multi_db_live, test_systems_live need SPID3R_DB_DRIVER=postgres|mysql|mariadb + a live server.
  • Without APP_ENV=testing the cache defaults to the persistent file driver and login throttling can 429 later suites.
