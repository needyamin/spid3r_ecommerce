Spid3r Store — Developer Documentation

The complete guide for developers working on the store: the stack, the Spid3rWeb v2.0 Modern MVC architecture, every subsystem, the coding standards and the testing bar.

This project is a production-grade e-commerce application built on the Spid3r language and the Spid3rWeb v2.0 Modern MVC framework, maintained in needyamin/spid3r_ecommerce. All 16 build phases and the v2.0 Modern MVC upgrade are complete; 35 test suites run across both execution engines (tree-walk interpreter and bytecode VM) on SQLite, PostgreSQL and MySQL in CI on every push. Companion documents: ARCHITECTURE.md (framework architecture), API.md (endpoint reference), USER-GUIDE.md (behaviour), README.md (index), CONTRIBUTING.md (contribution rules).

What is this project?

Spid3r Store is a full online shop: catalog, cart, checkout, payments, fulfilment, returns, marketing (coupons, campaigns, gift cards, loyalty, referrals), customer accounts, an 8-module Admin SPA panel with RBAC, and the operational scaffolding (migrations, queues, caching, CI, deployment verification). It is deliberately built with the Spid3rWeb v2.0 framework rather than around it — when a capability was missing, the decision was documented and the capability added at the right layer.

Design philosophy. Server-rendered HTML first with progressive enhancement, paired with a unified Admin SPA shell. One canonical price list in integer minor units. Security enforced by the framework defaults, verified by an executable suite of 35 test files.

Request lifecycle

socket accept (keep-alive loop, graceful Ctrl+C shutdown)
 └─▶ Request parse (method, path, headers, query, body, cookies, multipart files)
      └─▶ Application.handle_request
           ├─ 0a. Method spoofing (`_method` / `X-HTTP-Method-Override` on POST)
           ├─ 0b. Origin check on POST/PUT/PATCH/DELETE  → 403 foreign origin
           ├─ 0c. CSRF layer 2: session token for cookie-session writes → 419
           ├─ 1. Static file? → public/ with traversal guard + binary-safe `/uploads/*`
           ├─ 2. Router match (GET/POST/PUT/PATCH/DELETE, :params, *wildcard, HEAD→GET)
           │      └─ no match → allowed-methods 405, else 404 page
           ├─ 3. True Onion Middleware (`(req, next)`): auth, guest, throttle:5,60,
           │      role:*, permission:*, cors, request_id, etag…
           ├─ 4. Controller (`req.validate_or_fail(rules)` → service → HTML/JSON/auto-coercion)
           └─ 5. Response — security headers are CLASS DEFAULTS + dynamic HSTS check
                 exceptions: typed (HttpException) → status+message page/JSON
                             anything else → generic 500, never leaks internals

Every response passes through the framework Response class, whose constructor sets the security header set (CSP, nosniff, frame-options, referrer-policy, COOP, permissions-policy, plus dynamic SPID3R_HSTS evaluation) — controllers cannot forget them.

Environment setup

  1. Install the Spid3r runtime (≥ 1.0). Verify with spid3r --version.
  2. Clone the repository: git clone https://github.com/needyamin/spid3r_ecommerce.git && cd spid3r_ecommerce
  3. cp .env.example .env and adjust. SQLite works with zero config.
  4. spid3r magic migrate → spid3r magic db:seed → spid3r magic serve.

Useful CLI (all under spid3r magic): serve [--port N], test [--filter X] [--engine vm], route:list, migrate, migrate:rollback, migrate:status, migrate:sync, db:seed, queue:work [--once], make:controller/make:model/make:migration.

First admin & seeding

The seeder (database/seeders/DatabaseSeeder.matrix) is idempotent and ships no users (never ship default credentials). It seeds: roles (admin, staff, customer), the full permission catalog, role→permission bindings, store settings (name, currency, tax, shipping fees, free-shipping threshold, return window, cart discount, DEV-ONLY webhook secret), the currency catalog (BDT base + USD/EUR display), and EN/BN navigation translations.

Register at /register, then promote with SQL:

INSERT INTO user_roles (user_id, role_id)
SELECT u.id, r.id FROM users u, roles r
WHERE u.email = 'you@example.test' AND r.slug = 'admin';
Note. Staff accounts with narrower permission sets are then managed directly in the Admin SPA (/admin/staff, /admin/roles) — no more SQL needed; lockout protection prevents demoting the last admin.

The layered architecture (Spid3rWeb v2.0 Modern MVC)

Requests flow strictly one way. Each layer has one job; skipping a layer is the code-review equivalent of a failed test.

Routing & arrow closures

Routes are registered in per-domain files using concise v2.0 req => ctl.action(req) arrow closures and assembled by routes/store.matrix in a fixed order (static paths before :slug captures). Middleware attaches fluently per route or group:

Route.get("/wishlist", req => ctl.wishlist_page(req))
     .name("wishlist")
     .middleware("auth");

Route.post("/admin/api/orders/:order_id/shipments", req => ctl.create_shipment(req))
     .middleware("permission:orders.manage");

Built-in aliases: auth (redirects browsers to /login, 401 JSON for /api/* or Accept: application/json), guest, throttle:N,MIN (cache-backed with X-RateLimit-* headers), request_id, etag, cors, plus app-registered Onion middleware role:* and permission:* in app/Middleware/StoreMiddleware.matrix.

Controllers & validate_or_fail()

Controllers do exactly three things: validate, delegate to a service, answer. Validation is a declarative rule map per use-case in app/Validators/, applied with req.validate_or_fail(rules), which validates, coerces types (int, float, bool, list, map), and throws validation_failed(v.error_messages(), v.first()) (422) automatically on failure:

public fn add(self, req) {
    req.validate_or_fail(CheckoutValidators.cart_add_rules());
    let ident = CartIdentity.from_request(req);
    self.carts.add(ident, req.int("product_id"), req.input("variant_id", null), req.int("quantity", 1));
    return self.respond(req, {"added": true, "cart_count": self.carts.item_count(ident)});
}

Typed request extractors available on every Request: req.string(key, def), req.int(key, def), req.float(key, def), req.bool(key, def), req.page(), req.per_page(default, max), req.only([...]), req.except([...]), req.cookie(name, def), req.signed_cookie(name, def), req.session(), req.flash(k, v), and req.user().

Services

Services own the domain. They are plain classes wired in constructors, never singletons with request state, and use native v2.0 {} map and [] list literals throughout. The store's services: ProductService, CategoryService, BrandService, InventoryService, CartService, CheckoutService, OrderService, PaymentService, ShippingService, FulfillmentService, ReturnService, CouponService, CampaignService, GiftCardService, AdvancedStoreService (wishlist, reviews, loyalty, referrals, tracking, support), CurrencyService, LocaleService, ImageService, AdminService, AuthService.

Multi-step writes wrap in DB.transaction(fn() { … }); any throw rolls back everything (see the checkout transaction).

Repositories & the QueryBuilder

All SQL lives in repositories/services through the QueryBuilder — parameterised, identifier-checked, dialect-aware. Reference snippets:

// read + paginate
let rows = DB.table("products")
    .where("status", "=", "published")
    .whereIn("id", ids)
    .orderBy("id", "DESC")
    .limit(n).get();

// atomic conditional decrement (the oversell guard)
let changed = DB.table("inventory")
    .where("product_id", "=", pid)
    .where("quantity", ">=", qty)
    .decrement("quantity", qty);
if changed == 0 { throw validation_failed({"quantity": "Not enough stock."}); }

// raw SQL is allowed only with bound params and static text
DB.statement("CREATE INDEX idx_x ON t (col)", []);
Remember. orderBy replaces (no secondary sort chaining); DB.statement executes stacked statements on SQLite — only ever pass static SQL with ? bindings.

Views (SpiderBD v2)

Templates are .bd.html powered by SpiderBD v2 (framework/View/BD.matrix): @extends/@section/@yield/@include, @if(a >= b and flag == true)…@elif(...)…@else…@endif, @foreach(x in list)…@endforeach (with automatic loop.index, loop.iteration, loop.first, loop.last, loop.count), @csrf, @method('PUT'), and {{ expr }} — dot-path aware and auto-escaped. The store uses zero raw-output tags. Controllers merge a shared "chrome" (app/Support/StoreChrome.matrix: currency + language switcher data, translated nav labels, cart & wishlist counts) into every page context so the layout is consistent store-wide.

Admin SPA & 8 modules

The merchant back-office (/admin, AdminController + AdminCatalogController) combines server-rendered templates with a fast unified Admin SPA shell (public/js/admin-spa.js) backed by GET /admin/api/module/:module and form/JSON mutation endpoints across 8 core modules plus sub-views: overview, orders, products (with base64 magic-byte gallery uploads, cover/reorder, variants), categories (cycle-guarded nested tree), brands, inventory (restock, signed adjustments, thresholds), customers, and settings (plus staff, roles, and coupons). Database constraint errors are translated cleanly into 409/422 validation errors via app/Support/DbErrors.matrix.

Migrations & dialects

spid3r magic make:migration create_x_table   # scaffolds + registers
spid3r magic migrate                          # runs pending (auto-synced)
spid3r magic migrate:sync                     # rebuild the registry from files
spid3r magic migrate:rollback / :status

The Schema builder emits dialect-aware DDL; Schema.table(t, fn) ALTERs columns onto existing tables. Indexes on existing tables are plain DB.statement("CREATE INDEX …") (MySQL has no IF NOT EXISTS; migrations run once). Rollback of index drops is dialect-branched: MySQL needs DROP INDEX name ON table, SQLite/PG do not. PostgreSQL servers must allow md5/trust auth for the app user — the runtime client does not speak SCRAM (see .env.example).

The money rule

Non-negotiable. Every amount is an integer number of minor units. 5000 means 50.00. Floats never touch money: not in storage, not in arithmetic, not in APIs. Display strings are produced only by Money.format / Fx.format.

app/Support/Money.matrix: to_minor("1,234.56") → 123456 (grouping accepted; anything unparseable — injection payloads included — yields 0, never a crash), to_major, format (symbol + thousands grouping).

app/Support/Fx.matrix converts display currencies in pure integer steps — major units are held on a 10⁴ basis-point scale so every intermediate stays integral, and only the final step rounds:

// 100000 minor BDT (base) at USD rate 12100 bps → 82645 minor USD
from_major_bp4  = minor * 10000 / 10^digits_from
base_major_bp4  = from_major_bp4 * rate_from_bps / 10000
to_major_bp4    = round(base_major_bp4 * 10000 / rate_to_bps)
to_minor        = round(to_major_bp4 * 10^digits_to / 10000)

Conversions round-trip (BDT→USD→BDT is lossless at 2 digits) and zero-decimal currencies (JPY) work. Filters entered in a display currency are converted back to base before querying.

The checkout transaction

CheckoutService.place_order is the heart of the store. One DB.transaction covers everything; a throw at any step rolls back the whole thing:

DB.transaction {
  1. quote()            cart summary (fresh DB prices) → volume discount
                        + coupon (server-validated)
                        + campaign (time-boxed, capped)
                        + gift card (atomic preview, capped at payable)
                        → tax (bps of discounted value) → shipping (zone rate)
  2. resolve_address    saved address (ownership-checked) or inline (validated)
  3. per line: inventory.reserve(product, null, qty, "sale", …)
                        ATOMIC conditional UPDATE — 0 changes ⇒ 422, rollback
  4. order + order_items INSERT (name/sku/price snapshots)
  5. coupon usage recorded + uses incremented
  6. gift card REDEEMED inside the transaction (atomic decrement);
     balance mismatch ⇒ throw ⇒ whole order rolls back
  7. cart emptied       → a repeated submit cannot double-charge
}

Discount stacking order: volume → coupon → campaign → gift card → tax → shipping. No discount can exceed the subtotal; shipping is computed on the discounted value; free shipping applies above a configured threshold.

Payment adapters

app/Services/Gateway/PaymentGateway.matrix defines CodGateway (fully wired: staff confirm collection) and HttpsGateway — a config-driven adapter for bKash/Nagad/SSLCommerz/Stripe reading {PROVIDER}_INIT_URL/_VERIFY_URL/_REFUND_URL/_API_KEY/_WEBHOOK_SECRET from the environment. Contract:

  • Unconfigured gateway → fail fast 400; it never pretends to process.
  • Verification is server-to-server — the gateway is queried with OUR payment id and the response must match the amount exactly. Client-side "success" is decorative.
  • Webhooks authenticate with HMAC-SHA256 over the RAW body; after verifying the signature the payment is verified a second time through the adapter.
  • Settlement is status-guarded and idempotent; refunds write a ledger row and return stock; OrderService.set_status(order, "paid") fires the loyalty/referral rewards exactly once.

Outbound SMS mirrors the contract (SmsGateway: log dev driver or http provider; fail-fast when unconfigured).

Shipping & fulfilment

ShippingService resolves a delivery price for an address:

  1. Skip zones whose country is set and differs (case-insensitive).
  2. A zone whose district list names the address district wins immediately (most specific).
  3. Otherwise the first zone with an empty district list is the country-wide fallback.
  4. The rate is the first active tier for (zone, method) whose [min_order_minor, max_order_minor] window contains the order value; it carries the delivery estimate.
  5. No match → the flat settings fee (Phase 7 behaviour, unchanged) — zones are opt-in.

FulfillmentService runs the shipment lifecycle preparing → shipped → in_transit → delivered (+ failed → shipped retry). Illegal transitions are refused; shipped_at/delivered_at are stamped once; confirming delivery settles the ORDER as delivered (unless cancelled/refunded/already delivered); closed orders cannot receive shipments. Multiple shipments per order support partial fulfilment, and the shipment row (carrier, tracking number, method, zone) is the integration point a courier API would fill.

Returns engine

ReturnService: only delivered orders of the requesting user, inside the window (default 14 days, measured from the latest shipment's delivered_at), quantity capped at what was bought. Transitions are guarded: requested → approved|rejected → received → refunded. Refunding restocks the items exactly once, records the refund capped at the historical line value, and writes a refunds ledger row when a payment exists (COD orders settle offline).

Catalog cache

The storefront's hottest reads are cached through the framework Cache facade with generation-based invalidation (app/Support/CatalogCache.matrix):

key = "store:catalog:v" + version + ":featured:8:BDT:base"
                                                   └ limit, currency, fx marker
Cache.remember(key, ttl, fn() { …query + decorate… })
  • Bump on every write that changes what shoppers see: product/category/brand writes, gallery uploads, stock movements (reserve/release — checkout, cancellations, returns), display-currency changes. The bump orphans every old entry at once — no wildcard flush, identical behaviour on every driver.
  • Bounded key space: only the UNFILTERED listing is cached (sort × page); filtered searches always hit the DB, so request params cannot poison keys.
  • Zero-query hits: entries store fully decorated rows (price strings, image URLs already resolved).
  • TTLs come from the container (home_ttl 120 s, product_ttl 300 s).
Duty. If you add a catalog write path and forget the bump, shoppers see stale data for up to 5 minutes. test_catalog_cache verifies the mechanism; the bump list is documented in CatalogCache.matrix — keep both honest.

Auth & RBAC

  • Passwords: bcrypt via the runtime native. Reset/verification tokens: stored hashed, single-use, expiring.
  • Sessions: sess_ + 24 random bytes, DB-backed with sliding TTL, revoked on logout, cookie HttpOnly + SameSite=Lax (+ Secure opt-in). Stateless JWT auth is also supported out-of-the-box by Spid3rWeb v2.0 (framework/Auth/Jwt.matrix) for API clients and TestClient.acting_as().
  • Authorization: role:admin middleware for pages, permission:x for APIs (checked via policies against role_permissions). Services re-check ownership (orders, returns, addresses) so a stolen id parameter buys nothing.
  • Throttling: login/register/reset 5/min, support 5/min, gift-card balance 20/min, estimate 30/min — cache-backed, 429 beyond the limit.

Multi-currency & language

Currency is display-only (see the money rule): the customer's choice lives in the store_currency cookie, is validated against the active catalog (tampered cookie → base currency), and converts at the display edge. Carts, checkout, orders and payments stay in the base currency — the footer states "Prices in X · Billed in Y". Language uses the translations table (locale → namespace → key → value) with the fallback chain requested → default locale → supplied fallback → key; the choice lives in store_locale (?lang= also works). Both are set via POST /locale and rendered by StoreChrome on every page.

Queues & notifications

Jobs are registered in routes/queue.matrix and processed by spid3r magic queue:work (database driver) or inline (sync). Store jobs: store.password_reset, store.email_verification, store.order_confirmation, store.support_ticket, store.sms_notification. The request path never depends on SMTP or a carrier round trip; the mail driver is log until the runtime ships outbound TCP.

CSRF: two layers

  1. Origin check on every state-changing method — a foreign Origin is a flat 403.
  2. Session token for cookie-session writes without an Origin header — missing/invalid → 419. Bearer/JSON API clients are exempt (browsers cannot attach cookies cross-site to them).

Input & uploads

  • Every write path validates through declarative rule maps via req.validate_or_fail(); numeric money parsing treats garbage as 0 (never a 500).
  • All SQL is parameterised; raw statements are static text with bindings only.
  • Uploads: magic-byte inspection (PNG/JPEG/GIF/WEBP), 2 MiB cap, random names, binary-safe write and binary-safe static serving for /uploads/*; refused payloads store nothing.
  • 500s render a generic message — driver errors can never leak SQL fragments.
  • The full matrix (and the executable checks) is in SECURITY.md.

Coding standards

  • Layer discipline: SQL only in repositories; logic only in services; controllers only translate HTTP; templates only render.
  • Modern v2.0 syntax: Use native { "key": val } map literals and [ ... ] list literals (never legacy map(...) or list(...)), arrow closures req => ... for route handlers, and req.validate_or_fail(rules) in controllers.
  • Naming: services end in Service, repositories in Repository; snake_case functions, snake_case columns; route names dot-notation (account.rewards).
  • Errors: throw typed helpers (validation_failed → 422, not_found → 404, forbidden → 403, unauthorized → 401) with field-keyed maps; never leak internals.
  • Comments explain why, and contracts live in the file header (every subsystem file opens with its rules — read those first).
  • No new dependencies — the framework composes runtime natives.

Spid3r gotchas

These bite everyone once. The list below is earned experience — check it before writing code.
  • public and other keywords cannot be identifiers; there is no ternary ?:; match is reserved (router method is match_any).
  • let i cannot be redeclared in one function scope — reuse or rename (j, k…).
  • Non-transitive imports: import "framework/Web" exports barrel functions (web(), model(), router(), route(), abort(), validate(), etc.), NOT class constructors (DB, Route, Response, Container). Import direct modules where class symbols are used.
  • String literals interpolate {var} — never write a literal {word} inside a .matrix string.
  • for x in list iterates copies — mutate via indexed access l[i] in a while loop.
  • class declarations are top-level only; as is a cast keyword (never a param name); none is a reserved builtin.
  • Closures capture outer locals by reference and cannot reassign scalar variables (mutate a map or list container instead); self works inside closures (DB.transaction(fn() { self.helper() })).
  • Order numbers embed lowercase hex — never case-fold them for lookups.
  • Map key assignment: write nested maps back explicitly (bucket = m[k]; bucket[x]=v; m[k]=bucket) — do not rely on in-place nested mutation.
  • Maps iterate in unspecified key order — sort deterministically at the source when order matters.

Walkthrough: adding a feature

The reviews feature is the reference implementation — copy its shape.

  1. Schema (database/migrations/0XX_….matrix): table + FKs + indexes + composite uniques; add to the registry via spid3r magic migrate:sync.
  2. Service (app/Services/…): the rules live here, e.g. verified purchase = 
    let lines = DB.table("order_items").where("product_id", "=", product_id).get();
let purchased = false;
let i = 0;
while i < lines.len() {
    let order = DB.table("orders")
        .where("id", "=", lines[i]["order_id"])
        .where("user_id", "=", user_id).first();
    if order != null and (order["status"] == "delivered" or order["status"] == "paid") {
        purchased = true;
        break;
    }
    i += 1;
}
if not purchased { throw forbidden("Only customers with a completed purchase…"); }
  3. Validator (app/Validators/…): declarative { ... } rule map for the write path.
  4. Controller: thin handler — req.validate_or_fail(rules) → service → respond(req, payload, fallback_path).
  5. Routes: register in the domain file with req => ctl.action(req) and middleware; descriptive SEO paths (/resource/:slug); JSON via format=json.
  6. View: template + shared chrome; escaped interpolation only.
  7. Admin surface (if moderation is needed): permission-gated API + queue page / Admin SPA module.
  8. Tests: add tests/test_….matrix (auto-discovered by TestRunner); cover the happy path, every refusal, and the permission boundary on both interpreter and --engine=vm.
  9. Docs: update the matching phase document, API.md and USER-GUIDE.md.

Cache invalidation duty

Any write that can change what shoppers see must call CatalogCache.bump_catalog_version() after the write commits. Current bump sites: product create/update/publish/delete, category and brand writes, image upload/reorder/delete, InventoryRepository.reserve/release (checkout, cancellations, returns, admin adjustments) and display-currency changes. The definitive list is the header of app/Support/CatalogCache.matrix.

Fixture & FK rules

  • Tag every fixture with string(unix_time()) and clean by that tag (slug/email prefixes) — never by blanket deletes.
  • FK-safe teardown order: refunds (by payment_id) → payments → shipments → coupon_usages → gift_card_transactions → loyalty_ledger → order_items → orders; cart_items before carts; inventory/order_items/cart_items before products; coupon_usages before coupons.
  • Wrap test bodies in try/finally { purge } — but keep the purge itself simple so it cannot throw and mask the real failure.
  • Authenticated flows must log in through the HTTP endpoint (the guest-cart merge lives there); constructing session cookies via services skips it.
  • ProductService.create needs brand_id/short_description keys and defaults to draft with 0 stock — pass status:"published" and set inventory in fixtures.

Performance

Load probe (in-process, tree-walk interpreter & bytecode VM, SQLite): /health ~3500 req/s · / ~250 · /catalog ~190 · search ~250 · /product/:slug ~110 · /cart ~150. Micro-benchmark results are tracked in benchmarks/RESULTS.md. The levers:

  • Indexes (migration 020): order_items(product_id), loyalty_ledger(order_id), coupon_usages(coupon_id), sessions(last_activity), jobs(queue, available_at), products(status, id) — plus the Phase 2 domain indexes.
  • Catalog cache — see above; a hit performs zero queries.
  • Batched reads — whereIn for images/products; never N+1 in listing paths.
  • Lazy images (loading="lazy" decoding="async") and static cache headers.

Honest limits: one reused DB connection per process (the runtime is single-threaded — pooling is a runtime feature); Redis waits on the runtime's redis native; no memory-profiler hook. Full statement in PERFORMANCE.md.
