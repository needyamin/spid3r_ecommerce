# Spid3r E-commerce — Development Tasks

## Project Objective

Build a complete, secure, scalable, and production-ready e-commerce application using the Spid3r programming language and Spid3r Web framework.

The application must use the actual capabilities and APIs available in both repositories.

**Important rules:**
- Do not invent Spid3r or Spid3r Web APIs.
- Inspect the existing source code and documentation before implementation.
- Reuse existing framework features wherever possible.
- Extend Spid3r or Spid3r Web only when genuinely necessary.
- Avoid unnecessary modifications to the language runtime.
- Write maintainable, modular, tested code.
- Do not leave placeholder implementations for required production features.
- Keep both repositories compatible.

# Architecture Requirements

Use a modular layered architecture:

1. Routes — HTTP endpoint registration.
2. Middleware — Request processing and access control.
3. Controllers — HTTP input and output handling.
4. Validators — Request validation.
5. Services — Business logic.
6. Repositories — Data access.
7. Models — Domain entities and data structures.
8. Events — Application events.
9. Jobs — Background processing.
10. Policies — Authorization rules.

### Architecture Rules

- Controllers must not contain complex business logic.
- Services must not depend unnecessarily on HTTP request objects.
- Database queries should be centralized in repositories.
- Payment logic must be isolated from order logic.
- Inventory operations must be transaction-safe.
- Shared functionality must be reusable.
- Secrets must never be committed to Git.
- All critical operations must have automated tests.

# Development Rules for AI Coding Agents

When implementing this project:

1. First inspect both GitHub repositories.
2. Read their READMEs and relevant source files.
3. Understand the actual Spid3r syntax.
4. Understand the actual Spid3r Web APIs.
5. Never assume another language's syntax works in Spid3r.
6. Never invent methods, classes, modules or functions.
7. Never modify working language features without a clear requirement.
8. If a framework capability is missing, document it before deciding where to implement it.
9. Prefer extending Spid3r Web over duplicating framework functionality in the application.
10. Implement one phase at a time.
11. Test every phase before proceeding.
12. Fix errors instead of suppressing them.
13. Maintain compatibility with the existing CI pipeline.
14. Keep documentation synchronized with implementation.
15. Never mark a task complete without verifying it.
16. Do not leave TODOs or fake implementations for required production functionality.
17. Preserve backward compatibility unless a breaking change is explicitly necessary.
